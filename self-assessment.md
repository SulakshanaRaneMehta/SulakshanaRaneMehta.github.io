## Professional Growth and Career Direction
Completing the Bachelor of Science in Computer Science program has changed the way I understand software development and the type of professional I want to become. I entered the program with a background in interior design and business administration, where I learned to balance creativity with practical constraints, listen to client needs, revise ideas when requirements changed, and explain decisions to people with different priorities. Computer science gave me a technical language for many of those same habits. I learned that successful software is not defined by code alone. It depends on requirements, architecture, data, algorithms, security, testing, documentation, and communication working together.
My coursework introduced me to C++, Python, Java, and JavaScript and helped me become especially interested in JavaScript and full-stack development. As I progressed through programming, database, security, testing, and web development courses, my interests became more specific. I moved from thinking primarily about visible interfaces to thinking about complete systems. A useful application requires a clear user experience, but it also requires dependable server logic, meaningful API contracts, appropriate data structures, reliable persistence, validation, error handling, and security controls. This broader perspective is one of the most important outcomes of my degree.
The program has also clarified my professional goals. I plan to pursue a full-stack or software engineering position after graduation, with a particular interest in opportunities in the Bay Area. I want to continue developing applications that connect user needs with dependable technical implementation. My immediate priorities are to present my work through a strong professional ePortfolio, continue improving my interview and communication skills, and gain practical experience in a professional development environment. As my career develops, I am also open to a focused cloud or database certification once I know which technologies are most relevant to the roles I pursue.
Developing the ePortfolio has helped me see my work as evidence of professional capability rather than as a collection of completed assignments. To present an artifact effectively, I have had to explain why a design choice matters, what limitation it addresses, how it was verified, what trade-offs were involved, and how another developer or employer could evaluate the result. That process has strengthened my ability to communicate technical work with a clear purpose and has helped me identify the professional values I want to carry forward. Those values include maintainability, security, evidence-based decision making, respect for user needs, careful testing, and documentation that makes software easier for other people to understand.
## Collaboration and Communication
Computer science work rarely succeeds in isolation, even when an individual developer is responsible for a specific implementation. Collaboration requires more than dividing tasks. It requires making decisions visible, communicating assumptions, responding constructively to feedback, and creating work that another person can review, test, and continue. Throughout the program, I have become more deliberate about explaining design decisions and considering how technical information should be adapted for different audiences. The CS 499 code review strengthened this skill because I had to discuss existing functionality, identify limitations, and explain planned improvements in a way that was technically accurate without becoming unnecessarily difficult to follow.
Stakeholder communication has also been important to my development. My earlier background taught me to begin with the problem a client is trying to solve rather than with the solution I personally prefer. That perspective carried into computer science coursework where software requirements had to be translated into architecture, user flows, data models, interfaces, and testable behavior. I learned that communication is part of implementation because unclear requirements can create technical rework, while a clear explanation of constraints and trade-offs can support better decisions before code is changed.
## Examples From Prior Coursework
One useful example comes from CS 230 and the Game Room case study. In the Module Four journal, I worked from the perspective of the Product Owner and considered how a web-based game should coordinate client-side and server-side responsibilities through a RESTful API. The role required me to keep user needs, platform compatibility, security, scalability, and future expansion in view at the same time. I had to think about how client developers, server developers, and other technical contributors would rely on a shared API contract while still working on different parts of the system. This experience strengthened my understanding of stakeholder communication because a Product Owner must translate desired user behavior into requirements that developers can implement and evaluate. It also showed me that collaborative software decisions depend on clear boundaries and shared expectations rather than on every contributor working in the same part of the codebase.
CS 300 provided a different kind of decision-making experience through the ABCU advising project. The project required the same course-information problem to be considered with a vector, hash table, and binary search tree. The design work included reading and validating course data, creating course objects, producing an alphanumerically ordered course list, retrieving an individual course and its prerequisites, and comparing worst-case runtime and memory behavior. The important lesson for me was that a data structure should be selected from the operations the system must perform, not simply from familiarity with a particular implementation. Comparing the structures through Big O reasoning made performance trade-offs part of the design process before coding began, which later helped me explain the choices behind indexed lookup, filtering, sorting, and pagination in more complex applications.
CS 405 gave me direct experience with secure coding and defensive testing. In the buffer overflow activity, I examined a C++ program that copied unvalidated user input into a fixed-size character buffer, allowing adjacent memory to be overwritten. I changed the input path so the value could be checked safely before copying, rejected input that exceeded the buffer limit, used a size-aware copy operation, and tested normal, boundary-length, and overflow cases. The overflow attempts were rejected while the adjacent account number remained unchanged. Later security-policy work expanded that lesson from one defect to a broader development process through input validation, default-deny behavior, least privilege, defense in depth, quality assurance, secure coding standards, risk assessment, automated analysis, encryption, and authentication, authorization, and accounting controls. Together, these assignments changed security from a feature I might add later into a set of design assumptions that should guide implementation and testing from the beginning.
These earlier course experiences complement the capstone because they show the same professional habits in different contexts. The Game Room work emphasized role-based communication and translating user needs into system responsibilities. CS 300 emphasized algorithmic evaluation and explicit trade-offs before implementation. CS 405 emphasized anticipating misuse, validating boundaries, testing failure conditions, and formalizing secure practices. Together with the CS 499 code review, instructor feedback, and reproducible technical documentation, these examples provide broader evidence for the collaborative, communication, algorithmic, computing-practice, and security outcomes than the Travlr artifact could provide by itself.
## Data Structures, Algorithms, Software Engineering, and Databases
My coursework taught me to treat data structures and algorithms as design choices rather than abstract topics that exist only in textbook exercises. CS 300 made this concrete by requiring the same advising problem to be considered with vector, hash-table, and binary-search-tree structures and by connecting pseudocode to runtime and memory analysis. An implementation can be functionally correct and still be poorly suited to its scale, usage pattern, or maintenance needs. I learned to ask what operations matter most, how often they occur, what data must be retained, and what cost is introduced by searching, sorting, indexing, or transforming information. This way of thinking became especially important when working with collections, keyed lookup, filtering, sorting, pagination, and database queries.
Software engineering courses expanded that reasoning from individual algorithms to complete systems. I learned to separate responsibilities, use reusable components and services, validate data at appropriate boundaries, design predictable error behavior, and test changes so that one improvement does not introduce failures somewhere else. I also learned that maintainability is a technical requirement. Clear interfaces, consistent naming, focused modules, documented assumptions, and repeatable verification reduce the cost of future changes and make collaboration more effective.
Database work added another layer to this perspective. I learned that storing data is only one part of database design. Schema choices affect validation and future queries. Indexes can improve common access patterns but introduce storage and write costs. Migration work must preserve existing information while moving records toward a better structure. Pagination and server-side filtering can reduce unnecessary data transfer, while deterministic sorting and validation make API behavior more predictable. These experiences have prepared me to think about data as part of application architecture rather than as a separate backend concern.
## Security Mindset and Professional Responsibility
Security has become a design consideration that I expect to address from the beginning of a project rather than after functionality is complete. CS 405 reinforced this shift by moving from a concrete buffer-overflow vulnerability to a broader secure-development policy that included input validation, default deny, least privilege, defense in depth, quality assurance, automated analysis, encryption, and access-control principles. I learned to distinguish between interface restrictions and actual authorization. Hiding an administrative button, for example, does not protect a resource if a user can still reach an endpoint directly. Security controls therefore have to exist at the appropriate architectural layer and fail safely when credentials, data, or requests are invalid.
The same mindset applies to development and publishing practices. Environment files, secrets, tokens, dependency folders, build caches, and other local artifacts should not be placed in a public repository simply because they exist in a working development directory. A professional submission should expose the configuration structure needed to reproduce the project without exposing real secrets. This attention to secure defaults, validation, and responsible publication has become part of how I evaluate software quality.
My professional responsibility also includes recognizing that tools and technologies change. A secure or appropriate choice today may need to be revised as dependencies, standards, attack methods, or organizational requirements evolve. For that reason, I want to continue developing the habit of reviewing assumptions, using established libraries and practices, testing changes, and documenting why a solution was chosen. I see security as part of professional judgment rather than as a single feature.
## How the ePortfolio Artifacts Fit Together
The technical artifacts that follow this self-assessment show one application progressing through several levels of improvement. The original Travlr Getaways project was created in CS 465 as a MEAN stack application using MongoDB, Express, Angular, and Node.js. It included a customer-facing site, an administrator single-page application, REST API routes, Mongoose models, and JSON Web Token authentication. Using the same original project for all three CS 499 enhancement categories allowed me to demonstrate growth without separating that growth into unrelated examples.
The first enhancement focuses on Software Design and Engineering. It improves the administrator workflow through protected routing, route-based editing, shared validation, clearer API behavior, safer authentication logic, and more maintainable separation of responsibilities. This stage shows how an application that already works can be redesigned to become easier to understand, safer to use, and easier to maintain.
The second enhancement focuses on Algorithms and Data Structures. It introduces a catalog layer that uses appropriate collection structures for indexed lookup, unique resort values, search and filtering, deterministic sorting, pagination, validation, and complexity analysis. This stage demonstrates algorithmic reasoning and the ability to explain trade-offs between direct lookup, linear processing, sorting cost, simplicity, and scalability.
The third enhancement focuses on Databases. It converts price data to a numeric representation, adds an explicit nights field, strengthens schema rules, migrates legacy records with backup and validation, creates named indexes, and moves active catalog filtering, sorting, pagination, and search into MongoDB queries. This stage demonstrates that the best location for computation can change as a system grows. Logic that is useful for demonstrating in-memory algorithmic behavior is not always the best production architecture for larger persistent datasets.
Together, the artifacts demonstrate the range of skills I want an employer to see. The code review and written narratives show professional oral and written communication. The enhancement sequence shows algorithmic decision making, modern full-stack development, database design, testing, verification, and security-aware engineering. The final project also shows my ability to revisit earlier work critically, preserve what is useful, replace what no longer fits the problem, and explain the reasoning behind those decisions.
The instructor feedback throughout the capstone confirmed that the milestone submissions met the assignment expectations and did not require additional technical corrections. Rather than adding unnecessary features after successful verification, I used the final stage to improve the clarity, organization, and professional presentation of the work. This decision reflects an important lesson from the program. Improvement is not always measured by adding more code. It can also mean reducing ambiguity, strengthening evidence, protecting sensitive information, and making a solution easier for another person to evaluate and continue.
As I complete the program, I see the ePortfolio as both a record of what I have learned and a starting point for continued professional development. My strongest interest remains full-stack software engineering, but I now approach that goal with a broader understanding of algorithms, databases, testing, security, communication, and long-term maintainability. The portfolio demonstrates that I can move from requirements to implementation, evaluate design trade-offs, verify behavior, communicate technical decisions, and improve an existing system in a structured way. Those are the skills I intend to continue developing as I move from academic projects into professional software development.
